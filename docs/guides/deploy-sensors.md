# Manage sensor scripts centrally

PRTG Multi-Platform Probes run their own monitoring scripts through the
**Script v2 sensor**. This repository manages those scripts centrally and
rolls them out over the same restricted channel that already distributes the
MPP configuration.

A script is therefore not maintained on the probe: it is versioned here in
the repository and pushed to any number of probes with one command - from the
sensors page of the web interface, or from the shell.

## Commands

| Task | Command |
| --- | --- |
| show available sensors | `./prtg-nats sensor list` |
| details of one sensor | `./prtg-nats sensor show NAME` |
| deploy to one probe | `./prtg-nats sensor deploy NAME USER` |
| deploy to every probe | `./prtg-nats sensor deploy NAME --all` |
| show the sequence only | `./prtg-nats sensor deploy NAME USER --dry-run` |
| prepare a probe for sensors | `./prtg-nats sensor prepare USER` |
| prepare every probe | `./prtg-nats sensor prepare --all` |
| state of one probe | `./prtg-nats sensor status USER` |
| state of the whole fleet | `./prtg-nats sensor status --all` |
| reserve a test interface | `./prtg-nats sensor reserve NAME USER IFACE` |
| release a reservation | `./prtg-nats sensor release NAME USER IFACE` |
| deploy a credential profile | `./prtg-nats sensor profile NAME USER PROFILE --from-file FILE` |
| remove a profile | `./prtg-nats sensor profile NAME USER PROFILE --remove` |
| remove a sensor | `./prtg-nats sensor remove NAME USER` |

Sensors that measure against a self-operated endpoint additionally need
`./prtg-nats iperf-server` - see
[measurement endpoints](#measurement-endpoints).

## How a rollout runs

Deployment is transactional and follows the same steps as rolling out the MPP
configuration:

1. Every file of the sensor is transferred individually and staged on the
   probe. The helper there checks each file itself - shebang, Python syntax,
   size and freedom from control characters.
2. `sensor-activate` saves the previous state, installs the new files with
   the right permissions and creates the sudo rule.
3. The **self-test** runs: the probe calls the freshly installed script with
   `--self-check` - as the service user, through `systemd-run`, with the same
   hardening `prtg.mpprobe.service` uses. Only if that produces valid
   Script v2 JSON with `"status": "ok"` does the activation count as
   successful. The hardening values are read from the running unit, so the
   reproduction stays faithful even if Paessler changes them later.
4. If the self-test fails, the helper restores the previous state. No
   half-deployed sensor is left on the probe.

That also proves the permission chain, not just the file: a script that
cannot reach its privileged helper through `sudo` does not get through.

A rollout that fails earlier - a connection lost between two files, a probe
that stops answering while staging - is rolled back too, and that rollback
restores only what step 2 actually replaced. A sensor that was already
running is therefore still running afterwards, in the version it had before
anyone touched it. Helper versions below 3 removed it instead, so a failed
update took the working sensor with it; update the helper before the next
rollout if a probe still reports one of them.

## What is created on the probe

| File | Owner | Mode |
| --- | --- | --- |
| `/opt/paessler/share/scripts/NAME.py` | `root:SERVICE-USER` | `0750` |
| `/usr/local/sbin/prtg-sensor-NAME` | `root:root` | `0755` |
| `/etc/systemd/system/prtg-sensor-NAME.socket` | `root:root` | `0644` |
| `/etc/systemd/system/prtg-sensor-NAME@.service` | `root:root` | `0644` |
| `/run/prtg-sensor-NAME.sock` | `root:SERVICE-USER` | `0660` |
| `/etc/prtg-nats/sensors/NAME/version` | `root:root` | `0644` |
| `/etc/prtg-nats/sensors/NAME/shebang`, with dependencies only | `root:root` | `0644` |
| `/etc/prtg-nats/sensors/NAME/profiles/*.env` | `root:root` | `0600` |
| `/etc/NetworkManager/conf.d/99-prtg-sensor-interfaces.conf` | `root:root` | `0644` |

The service user is determined on the probe (`paessler_mpprobe` on MPP 3.10),
not dictated by the server.

Only text travels over the channel. The systemd units are generated by the
helper on the probe itself, from the validated sensor name. A faulty or
malicious caller cannot smuggle in its own unit or its own target path that
way.

## How a sensor gets root privileges

**Not through sudo.** `prtg.mpprobe.service` runs with `NoNewPrivileges=yes`,
and the kernel then ignores the setuid bit of `sudo` entirely. The vendor
means it exactly that way - the comment in the unit names precisely the case
of adding the service user to the sudoers file.

Instead, every sensor that ships a `privileged/` program gets its own small
service:

- a socket unit listens on `/run/prtg-sensor-NAME.sock`, accessible only to
  root and the group of the MPP service user;
- `Accept=yes` starts one instance of the template unit per connection and
  attaches the connection directly to its stdin and stdout.

For the privileged program nothing changes: it stays an ordinary filter
program that reads JSON and writes JSON, and can still be run by hand as root
for testing. The sensor script in turn only opens an `AF_UNIX` socket - the
one address family besides IP and netlink that the MPP unit's
`RestrictAddressFamilies` allows.

The detour has a second benefit: as its own service, the privileged program
is not subject to the seccomp rules of the MPP unit. A DHCP request needs
`AF_PACKET`, and the MPP unit does not allow that.

`./prtg-nats sensor status USER` shows this state as `helper=listening`.

## Prerequisite: a current probe helper

The sensor commands are executed on the probe by
`/usr/local/sbin/prtg-nats-probe-helper`. Probes enrolled before sensor
management existed do not know them yet and answer with
`Unsupported management request`.

The helper is renewed over the restricted channel, against a signature the
probe checks first - the management key opens the channel, but it does not
authorise new code on the far side
([ADR 0006](../architecture/decisions/0006-signed-helper-updates.md)):

```bash
./prtg-nats probe helper-update USER
```

The interface does the same thing with "Update helper" on the probe page.

A probe that reports no `helper_version` at all was enrolled before signed
updates existed. It carries no key to check a signature against, so it needs
the bootstrap path exactly once - and from then on the command above works:

```bash
./prtg-nats probe enroll ADMIN@HOST --reenroll
```

The NATS account comes from the inventory of the enrolled host; the bootstrap
login on `ADMIN@HOST` asks for the password of that account once - see
[the command reference](../reference/cli.md).

`./prtg-nats sensor status USER` shows where a probe stands.

## Layout of a sensor in the repository

```text
sensors/NAME/
  manifest.env                 # name, version, description, file list
  script/NAME.py               # Script v2 sensor, runs as the service user
  privileged/prtg-sensor-NAME  # optional helper with root privileges
  requirements.txt             # optional, creates a venv on the probe
  README.md                    # parameters and PRTG setup
```

The manifest names the files:

```ini
SENSOR_NAME=example
SENSOR_VERSION=1
SENSOR_DESCRIPTION=Short description for the catalogue
SENSOR_SCRIPT=script/example.py
SENSOR_PRIVILEGED=privileged/prtg-sensor-example
SENSOR_REQUIREMENTS=
```

## Rules for a sensor script

`./tests/check-static.sh` enforces these; without them a sensor does not pass
CI:

- Python 3 with `#!/usr/bin/env python3` as the first line.
- **Always exit code 0.** PRTG discards the output of a script that ends any
  other way - even when the JSON would be correct. Failures are reported via
  `"status": "error"`, not via the exit code.
- Parameters arrive **on stdin** as a single string and are split with
  `shlex.split()` and `argparse`. The bundled examples under
  `/opt/paessler/share/doc/examples/scripts/python` on every probe show the
  pattern.
- `--self-check` is mandatory: with it the sensor verifies only its own
  ability to run and returns valid Script v2 JSON. Deployment depends on it.
- A caught exception is never copied into the sensor message - it can contain
  credentials.

### Lookup channels

A yes/no channel gets its text from a lookup - **and its state along with
it**. `prtg.standardlookups.yesno.stateyesok` maps `1` to *Yes (OK)* and `2`
to *No (Error)*; it does not know a `0`, so PRTG shows "undefined lookup
value" and downgrades that to a warning instead of an error. A channel that
is meant to explain rather than complain therefore needs a lookup without an
error state - otherwise the sensor turns red although nothing is broken.

Which ones exist and what they trigger is described in
[PRTG lookups](../reference/lookups.md); the files themselves live under
[lookups/](../lookups/) as reference material. This repository does not deploy
custom lookups.

If a sensor needs elevated privileges, they belong in a separate program
under `privileged/`. It reads its task as JSON from stdin and writes the
result as JSON to stdout - nothing more; systemd takes care of the socket.
The sensor script itself stays unprivileged and sends the task over the
socket, so no credentials appear in the process list.

## Dependencies from PyPI

If a sensor ships a `requirements.txt`, deployment creates a dedicated
environment on the probe under `/var/lib/prtg-nats-sensors/venv/NAME` and
points the installed script's shebang at it. This is necessary because Debian
no longer allows system-wide `pip` installs since PEP 668.

That rewrite means the installed file is not byte-identical with the one in
the catalogue, and the deviation check compares exactly those bytes. The
helper therefore records the line the catalogue shipped under
`/etc/prtg-nats/sensors/NAME/shebang` and puts it back before it reports the
checksum; every other byte, and a shebang the helper did not write itself,
stays visible as a deviation. A probe still running helper version 1 reports
such a sensor as "Modified" for good, which
[the troubleshooting page](troubleshooting.md#a-sensor-reports-as-modified-right-after-deployment)
covers.

The probe needs two things for it:

- **`python3-venv`.** Debian splits `ensurepip` into its own package; without
  it `python3 -m venv` fails. The probe takes care of that itself: if the
  package is missing, the helper installs it during deployment. The package
  name is fixed inside the helper - the management channel cannot be used to
  pull in arbitrary packages.
- **Access to a package index.** In isolated networks, point `/etc/pip.conf`
  on the probe at the internal mirror - the repository does not dictate an
  index.

To run that step up front and check it in isolation, instead of discovering
it inside a running deployment transaction:

```bash
./prtg-nats sensor prepare mpp-probe-01
```

The command installs the missing prerequisites and reports which Python the
probe brings. With `--all` it runs across the whole fleet; individual
failures are counted and named at the end.

Both require a probe helper that knows this version of sensor management.
Older probes answer with `Unsupported management request` and need
`probe helper-update` first (see above).

Sensors that get by with the standard library need no `requirements.txt` and
run on the system Python.

## Credentials

Two ways are available:

1. **As sensor parameters in PRTG.** Simple, but PRTG stores the parameters
   in the core and shows them in the sensor settings.
2. **As a profile on the probe.** PRTG only sees the profile name; the
   password lives in a `0600` file that only the privileged helper reads. The
   service user the sensor runs as cannot get at it.

The second way is the recommended one. Profiles are maintained centrally
under `runtime/sensor-profiles/NAME/PROFILE.env` - in the same protected,
git-ignored area as the NATS passwords:

```bash
./prtg-nats sensor profile wlan-auth mpp-probe-01 office --from-file profile.env
```

The first call takes the file into the central store and deploys it; later
calls without `--from-file` distribute the stored state again.

## Measurement endpoints

A sensor can measure against a **self-operated far end** instead of a third
party service - `iperf-throughput` does that against an iperf3 measurement
endpoint. Such a far end is more than a credential profile: it is a machine
that wants setting up, and both sides have to know the same secret.

That is why it has its own command, and it works like `install-mpp`: one SSH
sign-in, and the machine is operational.

```bash
sudo ./prtg-nats iperf-server install root@iperf.example.com
sudo ./prtg-nats sensor deploy iperf-throughput --all
```

**The password is created on the NATS server and sent to the endpoint**, not
the other way round. The endpoint stores only a SHA-256 of the credentials -
a password created there could not be read back after the run and would have
to be copied off the screen. Created centrally, it lives under
`runtime/iperf/NAME.env`, in the same protected area as the NATS passwords.

| Task | Command |
| --- | --- |
| set up an endpoint | `./prtg-nats iperf-server install ADMIN@HOST` |
| show configured endpoints | `./prtg-nats iperf-server list` |
| values of one endpoint | `./prtg-nats iperf-server show NAME` |
| deploy credentials | `./prtg-nats iperf-server deploy NAME USER\|--all` |
| revoke credentials | `./prtg-nats iperf-server revoke NAME USER\|--all` |
| change the password | `./prtg-nats iperf-server install ADMIN@HOST --name NAME --rotate` |
| forget an endpoint | `./prtg-nats iperf-server forget NAME` |

**The credentials reach the probe as a profile**, over the path from the
previous section. The profile is named after the endpoint; as long as only
one is configured, also `default`, so the sensor works without `--profile`.

**Whoever deploys the sensor deploys the credentials with it.** A sensor
without them would only report `credentials-unreadable`; `sensor deploy`
therefore takes care of the step itself. Which sensors are affected is stated
by the `SENSOR_IPERF` field in their manifest.

**The endpoint gets no permanent access.** Unlike a probe it is not managed,
only measured; every intervention signs in anew. That includes the password
change - which in turn updates every probe that already has the endpoint.

For an endpoint this server cannot reach over SSH,
[the sensor README](../../sensors/iperf-throughput/README.md#set-up-the-endpoint-by-hand)
describes the same path by hand.

## Removing

```bash
./prtg-nats sensor remove NAME USER
```

Removes script, helper, systemd units, configuration including profiles, and
the virtual environment. Reserved test interfaces are handed back to
NetworkManager.

Taking a whole probe out of service clears all of its sensors in one go -
see [Retire a probe](operations.md#retire-a-probe).

To take back a single reservation - say, the wrong interface was picked -
this is enough:

```bash
./prtg-nats sensor release NAME USER IFACE
```

The interface returns to NetworkManager's management immediately; sensor,
profiles and remaining reservations stay untouched.

## Available sensors

| Sensor | Purpose | Details |
| --- | --- | --- |
| `wlan-auth` | check Wi-Fi sign-in (WPA2-PSK, PEAP, EAP-TLS) | [README](../../sensors/wlan-auth/README.md) |
| `internet-speed` | measure the throughput of the uplink (download, upload, latency) | [README](../../sensors/internet-speed/README.md) |
| `link-quality` | reachability and quality of the uplink (loss, latency, jitter) | [README](../../sensors/link-quality/README.md) |
| `iperf-throughput` | the uplink against a self-operated iperf3 endpoint (throughput, loss, jitter, latency) | [README](../../sensors/iperf-throughput/README.md) |

`internet-speed` and `link-quality` answer two different questions about the
same line: one asks how much it carries, the other how cleanly it carries.
A line with full throughput and 3 % packet loss passes every throughput test
and makes telephony unusable.

`iperf-throughput` measures the same line once more, but against
[your own endpoint](#measurement-endpoints) instead of the internet: not
"does the provider deliver the contracted line" but "can the site do its
work".
