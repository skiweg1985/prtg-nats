# Languages and translation

The interface ships English and German. English is the source language; German
is a full translation, not a partial one.

## The rule the whole thing rests on

**The backend never returns prose.** It returns a stable code, a translation
key and structured parameters. The browser turns that into a sentence.

```json
{
  "error": {
    "code": "probe.unreachable",
    "message_key": "errors.probe.unreachable",
    "params": { "probe": "mpp-probe-01" },
    "details": "ssh: connect to host … port 22: Connection timed out",
    "correlation_id": "01JC…",
    "retryable": true
  }
}
```

`message_key` and `params` are translated. `details` is the machine's own words
and is never translated - an administrator needs it verbatim.

The same applies to job log lines, audit actions and reconciliation plans. Each
carries a code and parameters; none carries a sentence.

That is what makes the platform translatable rather than only its static
labels. A German operator watching a rollout reads German, including the line
that says which file was transferred to which probe.

## Adding a language

1. Copy `web/frontend/src/i18n/locales/en.json` to `<code>.json` and translate
   the values.
2. Add the code to `SUPPORTED_LANGUAGES` and `LANGUAGE_LABELS` in
   `web/frontend/src/i18n/index.ts`.

No component changes. A key the new file is missing falls back to English -
an untranslated sentence is still usable, a raw key is not.

## What CI checks

`npm run i18n:check` fails on four things. The first three reach a user as an
empty label or a raw key on screen:

- a key present in one language and not the other, in either direction;
- an interpolation placeholder that differs between the two, so one language
  renders `{{probe}}` literally;
- an error code the backend can emit for which no message exists on this side.

The fourth is the other direction, and comparing the languages against each
other can never catch it: a key no line of code asks for. A string translated
into both languages and used nowhere reads as a feature that exists, and ten of
them read as an interface somebody half-built.

A key counts as used when it appears as a literal anywhere in `src/` - in
`t()`, in a table like the navigation's `labelKey`, or in `i18n.exists()` -
or when it sits under a prefix something builds keys from, as in
`` t(`jobs.filters.${entry}`) ``. Whole key spaces the backend fills in one
code at a time are listed in the script as such: `errors.`, `jobs.events.`,
`jobs.steps.`, `deviations.`, `roles.`, `audit.actions.`, `plan.` and
`jobs.blocked.`. Their completeness is checked from the other side - by the
error-code check above, and by
[tests/check-job-messages.py](../../tests/check-job-messages.py) for the job
log.

A string written before the screen that will use it goes in the script's
`AHEAD_OF_THE_INTERFACE` list with the reason. Everything else that nothing
asks for is a leftover: translate what exists.

The same checks run as unit tests, so the editor catches them before CI does.

## Rules for writing UI text

- No literal text in a component. Every string comes from the table.
- Numbers, dates and durations go through `Intl`, never through a translation
  string. A locale that formats "2 min" differently is a locale problem, and
  `Intl` already knows the answer.
- A status enum needs a label in every language. A test asserts that, because a
  missing one renders as a raw key inside a badge - the kind of thing nobody
  notices until it is in front of a customer.
- Keep the German informal-but-precise register the rest of this project uses.
  "Die Probe antwortet nicht", not "Ein Fehler ist aufgetreten".

## Documentation

The documentation is English only for now. Every page carries front matter with
`title`, `role` and `updated`, and the structure is task-based rather than
file-based, so a translated tree can be added later without moving anything.
